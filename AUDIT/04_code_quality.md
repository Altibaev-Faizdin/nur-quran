## 2. Детальный разбор архитектурных проблем и дефектов качества кода

### 🔴 ARCH-01: Тройное дублирование аудиодвижка и фрагментация состояния
- **Файлы:**
  1. `frontend/pages/quran.html`, строки 240–320 (`playAyahQuran`, `togPlay`, `nextA`, `prevA`, `onAyahEnded`)
  2. `frontend/shared.js`, строки 1250–1320 (`quickPlay`, `togPlay`, `stopSurah`, `closeAudio`, `seekAudio`)
  3. `frontend/reciter-player.js`, строки 1–685 (`PlayerState`, `playAyahAt`, `togglePlay`, `playNext`, `playPrev`, `seekTo`)
- **Проблема:**
  В проекте сосуществуют три совершенно изолированных аудиоплеера с разной структурой данных, разными элементами DOM и разными протоколами управления:
  - Плеер в `quran.html` воспроизводит только чтеца Мишари Рашида аль-Афаси по отдельным аятам через `cdn.islamic.network`.
  - Плеер в `shared.js` воспроизводит полные суры из выпадающего списка на `reciters.html` и главной странице через прямое обращение к серверам `mp3quran.net`.
  - Плеер в `reciter-player.js` имеет сложную систему поаятного и полного воспроизведения для 10 отдельных страниц чтецов.
- **Последствия:**
  - Отсутствие единого состояния: пользователь не может начать слушать суру на странице чтеца и продолжить чтение текста на странице Корана.
  - Логика исправления багов (таймауты, fallback-серверы, индикаторы загрузки) не распространяется между плеерами.
- **Рекомендация:**
  Создать единый синглтон-модуль `AudioManager` в `shared.js` (или `audio-engine.js`), управляющий единственным экземпляром `HTMLAudioElement`, состоянием воспроизведения, очередью аятов, кэшированием URL и MediaSession API.

### 🔴 ARCH-02: 2 780 строк дублированного кода в 10 страницах чтецов (`reciter-*.html`)
- **Файлы:** `frontend/pages/reciter-abdulbasit.html`, `reciter-ghamdi.html`, `reciter-minshawi.html`, `reciter-maher.html`, `reciter-alafasy.html`, `reciter-yasser.html`, `reciter-islam-sobhi.html`, `reciter-sherif-mostafa.html`, `reciter-abdurrahman-mossad.html`, `reciter-raad-kurdi.html` (суммарно 2 780 строк).
- **Проблема:**
  Каждая из 10 страниц чтецов на 95% состоит из идентичного кода:
  - 100% повторяющийся блок `<style>` (стили `.reciter-hero`, `.reciter-card`, `.big-play-btn`, `.progress-section`, `.seek-slider`, `.surahs-grid`, `.surah-btn`).
  - 100% повторяющаяся HTML-разметка плеера, нижней панели навигации, модальных окон и контейнера сетки сур.
  - Единственное отличие между файлами — имя чтеца в заголовке, фото и две константы в блоке скрипта:
    ```javascript
    const RECITER_ID = 'abdulbasit';
    const RECITER_SERVER = 'https://server7.mp3quran.net/basit/';
    ```
- **Последствия:**
  Любое изменение стилей, адаптивности, кнопок или добавление новой функциональности требует ручной правки 10 независимых HTML-файлов, что гарантированно приводит к расхождению версий и багам.
- **Рекомендация:**
  Объединить 10 страниц в один динамический шаблон `frontend/pages/reciter.html?id=abdulbasit`, который загружает метаданные чтеца из массива `RECITERS` в `shared.js`. Старые URL-адреса сохранить через Netlify redirects (например, `/pages/reciter-ghamdi.html` -> `/pages/reciter.html?id=ghamdi`).

### 🔴 ARCH-03: Три независимых калькулятора даты Хиджры и "мёртвый" эндпоинт бэкенда
- **Файлы:**
  1. `backend/api/views.py`, строки 139–147 (`hijri_date`, обращение к AlAdhan API)
  2. `frontend/shared.js`, строки 325–332 (`toHijri`, 10-строчный алгоритм вычисления юлианского дня)
  3. `frontend/pages/hijri.html`, строки 173–182 (`gregorianToHijri` через `Intl.DateTimeFormat`)
- **Проблема:**
  - Бэкенд реализует эндпоинт `GET /api/hijri-date/`, кэширует его на 12 часов и имеет unit-тесты. Однако во всём фронтенде нет **НИ ОДНОГО** вызова этого эндпоинта (`grep -rn "hijri-date" frontend/` возвращает 0 результатов).
  - Часы в шапке на всех страницах вычисляют дату Хиджры по арифметической формуле в `shared.js`, которая имеет погрешность ±1–2 дня от реального исламского календаря (основанного на наблюдении Луны).
  - Страница `hijri.html` использует третий способ — браузерный API `Intl.DateTimeFormat('en-US-u-ca-islamic')`.
- **Последствия:**
  В шапке сайта отображается одна дата Хиджры, а на странице `hijri.html` — другая!
- **Рекомендация:**
  Унифицировать вычисление даты Хиджры: фронтенд должен запрашивать дату с бэкенда `/api/hijri-date/` (кэшируя в `localStorage` на 24 часа), а при отсутствии сети использовать `Intl.DateTimeFormat` как надежный fallback.

### 🟠 CODE-04: 26 пустых блоков `catch` (Silent Failures)
- **Файлы:**
  - `frontend/pages/quran.html`, строки 246, 266 (`aud.play().catch(function(){});`)
  - `frontend/pages/tasbih.html`, строки 448, 462, 600
  - `frontend/pages/bookmarks.html`, строки 139, 145
  - `frontend/shared.js`, строки 38, 426, 440, 451, 456, 469, 474, 518, 623, 1006, 1146, 1337, 1349, 1364, 1369, 2108
  - `frontend/reciter-player.js`, строки 250, 258
- **Цитата кода (`quran.html:246`):**
  ```javascript
  aud.play().catch(function(){});
  PLAYING=true;set('plbtn','⏸');
  document.getElementById('abar').classList.add('show');
  ```
- **Проблема:**
  Браузер блокирует автовоспроизведение аудио (Autoplay Policy) или падает с ошибкой сети (404/ERR_INTERNET_DISCONNECTED). Блок `catch` перехватывает исключение и ничего не делает, но код после него немедленно переводит плеер в состояние `PLAYING=true` и меняет иконку на паузу `⏸`.
- **Последствия:**
  Пользователь видит, что плеер "играет" (кнопка в состоянии паузы, панель открыта), но в динамиках полная тишина. Нет ни тоста с ошибкой, ни попытки переключиться на альтернативный сервер.
- **Рекомендация:**
  В обработчике `catch` сбрасывать состояние плеера в `PLAYING = false`, возвращать иконку `▶` и вызывать `showToast('Unable to play audio. Check internet connection', 'error')`.

### 🟠 CODE-05: Сломанное событие `langChange` в системе интернационализации
- **Файлы:**
  - `frontend/pages/quran.html`, строка 320:
    ```javascript
    document.addEventListener('langChange', e => { CLANG = e.detail; if (CUR) openS(CUR.n); });
    ```
  - `frontend/i18n.js`, строки 106–109:
    ```javascript
    window.setLanguage = function(lang) {
      localStorage.setItem('lang', lang);
      applyLanguage(lang);
    };
    ```
- **Проблема:**
  Код страницы `quran.html` ожидает пользовательское событие `langChange` для перезагрузки перевода суры (на русский `ru.kuliev`, узбекский `uz.sodik` или английский `en.asad`). Однако функция `setLanguage()` в `i18n.js` **НЕ ОТПРАВЛЯЕТ** событие `langChange`!
- **Последствия:**
  При переключении языка в языковом меню интерфейс шапки меняется, но текст Корана остаётся на предыдущем языке до тех пор, пока пользователь вручную не перезагрузит страницу.
- **Рекомендация:**
  В `window.setLanguage` добавить вызов:
  ```javascript
  document.dispatchEvent(new CustomEvent('langChange', { detail: lang }));
  ```

### 🟡 CODE-08: Непрерывный холостой таймер 60 FPS в анимации курсора
- **Файл:** `frontend/shared.js`, строки 318–321
- **Цитата кода:**
  ```javascript
  setInterval(() => {
    tx += (mx - tx) * 0.12; ty += (my - ty) * 0.12;
    t.style.left = tx - 14 + 'px'; t.style.top = ty - 14 + 'px';
  }, 16);
  ```
- **Проблема:**
  Таймер `setInterval(..., 16)` работает непрерывно на частоте 60 раз в секунду на всех страницах приложения, в том числе когда мышь неподвижна или вкладка браузера неактивна. Каждые 16 мс выполняется принудительная запись в стили DOM-элемента (`t.style.left`, `t.style.top`), вызывая layout/style recalculation.
- **Последствия:**
  Повышенный расход батареи на ноутбуках и мобильных устройствах с подключённым указателем.
- **Рекомендация:**
  Перевести анимацию на `requestAnimationFrame` с условием остановки (засыпания), если расстояние между текущей и целевой точкой меньше 0.1px:
  ```javascript
  function animateCursor() {
    if (Math.abs(mx - tx) > 0.1 || Math.abs(my - ty) > 0.1) {
      tx += (mx - tx) * 0.12; ty += (my - ty) * 0.12;
      t.style.left = (tx - 14) + 'px'; t.style.top = (ty - 14) + 'px';
    }
    requestAnimationFrame(animateCursor);
  }
  ```
